# .ifreplay ファイル形式（v4）

Ifuto Replay が録画中に書き出すファイルの仕様です。

**設計方針**

- **追記専用**（append only）。録画中にファイル先頭へ戻る／シークする必要がないので、HDD でも速い
- **1パケット = 1フレーム** のストリーム。書く順番＝届いた順番
- **自分の対応表を持たない**。パケットID（可変長int）と中身は、バニラの PLAY 状態のコーデック
  （`PlayStateFactories` / `PacketCodecDispatcher`）が書いたものをそのまま保存する
- 将来のバージョン違いに備えて、**パケットの識別名（`PacketType.id()`）も別に残す**

---

## 全体の構造

```
[ヘッダ]
[レジストリ フレーム]    <- 録り始めに1回だけ（設定で省略可）
[フレーム] × N          <- パケット本体・種類定義・しおり
[インデックス フレーム]  <- 終了時にまとめて書く
[終了 フレーム]
[巻末 12バイト]        <- 終了時にまとめて書く
```

---

## 共通の型

| 名前 | 中身 |
| --- | --- |
| `byte` | 1バイト |
| `varint` | Minecraft と同じ可変長int（LEB128。7bit + 継続フラグ、最大5バイト、リトルエンディアン順） |
| `varlong` | 同上の64ビット版（最大10バイト） |
| `long` | 固定8バイト（ビッグエンディアン） |
| `string` | `varint` のバイト長 + UTF-8 のバイト列 |

---

## ヘッダ

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | magic | `byte[4]` | `I` `F` `R` `P` |
| 2 | version | `varint` | フォーマットバージョン（いまは `6`） |
| 3 | flags | `varint` | bit0: C2S（自分の操作）も含む / bit1: 圧縮が辞書を共有している（v2〜v3） / bit2: パケットをかたまりにまとめて圧縮している（v4〜） |
| 4 | mcVersion | `string` | 例: `1.21.11` |
| 5 | startedAt | `long` | 録画開始時刻（epoch ミリ秒） |
| 6 | serverName | `string` | 接続先。シングルプレイは `singleplayer` |
| 7 | playerName | `string` | 録画したプレイヤー名 |

## フレーム

最初の1バイト（正確には `varint`）がタグです。

### `0` TAG_END

録画の終わり。長さ0。これ以降は読まない。

### `5` TAG_REGISTRIES（動的レジストリの写し）

録り始めに1回だけ書かれる（設定 `saveRegistries` が OFF のときは書かれない）。
**パケットを復元するには、録ったときと同じレジストリ（バイオーム・次元・エンチャントなど）が
必要**なので、その時点の物をそっくり保存しておく。

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | packedLength | `varint` | 圧縮後のバイト数 |
| 2 | rawLength | `varint` | 展開後のバイト数 |
| 3 | data | `byte[packedLength]` | deflate した NBT |

NBT の中身は「レジストリの識別名 → エントリの配列」で、1エントリは
`{id: 識別名, data: (省略可) NBT}`。バニラがサーバーから受け取る
`SerializableRegistries.SerializedRegistryEntry` と同じ形。

これがあるおかげで、**録画ファイル単体で再生できる**（別の世界に居る状態でも、
録ったときとまったく同じレジストリを組み直せる）。

### `1` TAG_PACKET_TYPE（パケット種類の定義）

同じ種類のパケットは2回目以降この番号だけを書く（識別名を毎回書かない）。

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | index | `varint` | 0から順に振られる番号 |
| 2 | direction | `byte` | `0` = S2C（サーバー→クライアント） / `1` = C2S |
| 3 | identifier | `string` | 例: `minecraft:entity_position`（`PacketType.id()`） |

**必ず、その種類のパケット本体より先に書かれる。**

### `2` TAG_PACKET（パケット本体）

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | deltaMs | `varint` | 直前のフレームからの経過ミリ秒 |
| 2 | typeIndex | `varint` | TAG_PACKET_TYPE で定義した番号 |
| 3 | length | `varint` | このあとに続く「中身」のバイト数 |
| 4 | method | `byte` | `0` = そのまま / `1` = deflate / `2` = zstd（v6〜） |
| 5 | payload | `length` バイト | 下記参照 |

**payload の中身**

- `method = 0`（そのまま）
  - バニラのコーデックが書いた **「パケットID（varint） + 本体」** そのまま。
    つまり復号するときは、この列をそのまま PLAY 状態のデコーダに流せば元のパケットに戻る。
- `method = 1`（deflate）・`method = 2`（zstd）
  - 先頭に `varint` で **展開後の長さ** が入り、そのあとに圧縮された
    「パケットID + 本体」が続く。置き方は deflate と zstd で同じ。

圧縮は「設定で選んだとき」だけ、かつ「圧縮したほうが小さくなったとき」だけ使われる。

**bit1（辞書の共有・v2〜v3）が立っているとき** は、ファイル全体が **1本の deflate
ストリーム** になっている。パケット1個は数十バイトしかないので1個ずつ圧縮しても
ほとんど縮まないが、`reset()` せずに直前のパケットを辞書として使いまわす
（`SYNC_FLUSH` で区切る）と、同じ形式のパケットが続くこの種のデータは大きく縮む。

読み出す側は **必ず先頭から順に** 展開しないと状態がずれる。飛ばしてよいフレームは
`method = 0`（そのまま）の物だけで、`method = 1` の物は中身が要らなくても展開する
（`inflater` の状態を進めるため）。**v4 以降はこの枠を使わない**（次のかたまり方式）。

### `8` TAG_BLOCK（パケットのかたまり）

**bit2 が立っているファイル（v4〜）で使われる。** パケットを一定量ためて、
ひとまとめにして圧縮する。

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | rawLength | `varint` | 展開後のバイト数 |
| 2 | method | `byte` | `0` = そのまま / `1` = deflate / `2` = zstd（v6〜） |
| 3 | packedLength | `varint` | `method = 1・2` のときだけ。圧縮後のバイト数 |
| 4 | data | `packedLength`（`method = 0` なら `rawLength`）バイト | 中身 |

展開した中身には、パケットが入っている数だけ次が並ぶ:

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | deltaMs | `varint` | 直前のパケットからの経過ミリ秒 |
| 2 | typeIndex | `varint` | TAG_PACKET_TYPE で定義した番号 |
| 3 | length | `varint` | パケットの中身のバイト数 |
| 4 | payload | `length` バイト | 「パケットID（varint） + 本体」そのまま |

**かたまり1個は、それだけで完結した圧縮**（deflate なら `Z_FINISH` まで書いてある）。
したがって

- 読み飛ばしてもあとに影響しない（展開せずに `skip` できるので、一覧・しおりの
  読み出しが速い）
- **つなぎ合わせても壊れない**（クリップは区間ファイルをそのまま連結している）

かたまりの区切りは「目安の大きさまでためた（速い・標準: 64KB / 強: 256KB / 最強: 1MB）」
「2048個ためた」「1秒たった」「パケット以外の記録が来た」「録画を終える」のどれか。

実測（1.21.11 のパケット列を組み立てて計測・60秒ぶん。v5 までの deflate 方式）:

| 方式 | 込み合い（9.3MB） | チャンク多め（7.8MB） |
| --- | --- | --- |
| 1個ずつ deflate 9（v3 まで） | 29.3% | 22.2% |
| **かたまり deflate 8（v4・おすすめ）** | **23.9%** | **21.8%** |
| かたまり deflate 9（v4・最強） | 23.3% | 21.1% |
| かたまり deflate 6（軽い） | 25.5% | 23.5% |

（deflate 9 は 8 の約2倍CPUを使う。録画中に追いつかなくなりそうなときは、
自動的にレベル6へ落としてパケットの取りこぼしを防ぐ）

v6 からは「標準」以上で zstd を使う。zstd level 3 は deflate 6 より速くて小さく、
展開も約4倍速い（公開ベンチマーク値。実データでの計測は今後追記）。

自作の IFZ1（種類別レーン + LZ）も試したが、実測で zstd の約1.6倍の大きさに
なって勝てなかった。Huffman を足しても天井が zstd に届かない。前段の変換
（OpenZL 式の shuffle・delta・型順整列）も最大で数%どまり。よって既定は
zstd のまま。IFZ1 の残骸は計測用（`/replaybench`・CI の往復ゲート）に残す。
CI の合成データでの Java 実測: zstd-3 は 46.3%・25MB/s、IFZ1-fast は
70.1%・44MB/s（展開は 159〜203MB/s で zstd の 3〜4倍速いが容量1.5倍）。

### `7` TAG_LOCAL（クライアントの内側で起きた出来事）

サーバーから届く物はすべてパケットとして残るが、**クライアントが自分で湧かせた物**
（ブロックを崩しているときの破片、足あと、Mod の演出など）はパケットにならない。
それをこの枠で記録する。

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | deltaMs | `varint` | 直前のフレームからの経過ミリ秒 |
| 2 | subtype | `varint` | `0` = パーティクル / `1` = まとめたパーティクル（v5〜） |
| 3 | length | `varint` | 中身のバイト数 |
| 4 | data | `byte[length]` | 下記 |

`subtype = 0`（パーティクル）の `data` は 「NBT + `float` 6個」:

- NBT: `id`（パーティクルの種類の識別名）と `p`（種類ごとの引数を codec で NBT にした物）
- `float` 6個: x / y / z / velocityX / velocityY / velocityZ

`subtype = 1`（まとめたパーティクル）の `data` は「件数 + 件数ぶんの (長さ + 1件ぶん)」:

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | count | 固定4バイトint | 件数 |
| 2 | 繰り返し | 固定4バイトint + バイト列 | 長さ + `subtype = 0` と同じ1件ぶん |

件数が多いので1件ずつ枠を取ると書き込みが詰まる。まとめて1枠で書く
（32件または16KBたまるか、ティックごとに書き出す）。

**パケットを処理しているあいだに湧いた物は記録しない**（サーバーから届いた物として
すでに残っているので、二重に出てしまう）。記録は1秒あたり 160 件まで。

### `6` TAG_INPUT（パケットにならない操作）

マウスカーソル・入力中の文字・視点（F5）・デバッグ画面（F3）・開いている画面など、
**ローカルでしか起きない操作** の差分。パケットが1個も要らないほど小さい。

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | deltaMs | `varint` | 直前のフレームからの経過ミリ秒 |
| 2 | subtype | `byte` | `0` = カーソル絶対座標 / `1` = カーソル移動量 / `2` = 視点 / `3` = デバッグ画面 / `4` = 開いている画面 / `5` = 入力中テキスト（全文） / `6` = 入力中テキスト（増えた分） |
| 3 | length | `varint` | 中身のバイト数 |
| 4 | data | `byte[length]` | 先頭1バイトが種類（`subtype` と同じ）+ 種類ごとの中身 |

（v5 で種類を枠の先頭にも明示した。v4 以前は種類が中身の先頭にしかないが、
読み手がバージョンで吸収するので、そのまま読める）

### `3` TAG_MARKER（しおり）

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | deltaMs | `varint` | 直前のフレームからの経過ミリ秒 |
| 2 | name | `string` | しおりの名前（既定は `Marker 1`, `Marker 2` …） |

予約名（録画・編集側が自動で付ける。再生の一覧には出さない）:

| 名前 | 意味 |
| --- | --- |
| `__snap__` | 世界の写しがある場所。区間の先頭と、録り始め（途中参加でない場合）に付く。編集で切り出すときの起点 |
| `__start__` | 編集で先頭を落とした物の「ここから見せる」位置。再生・書き出しはここから始める |

### 巻末（ファイルの最後 12 バイト）

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | magic | `byte[4]` | `I` `F` `R` `P` |
| 2 | indexOffset | `long` | インデックス フレームが始まるファイル位置 |

**用途**: 一覧画面で「総時間」を出すために、本体を1バイトも読まずに末尾だけ見るため。
読み手は「ファイルサイズ - 12」から読んで、マジックが合えば `indexOffset` へ移動すればよい。
巻末が無い（古い・壊れた）ファイルは、TAG_END で読み終えた扱いにして総時間は不明として扱う。

### `4` TAG_INDEX（シーク用の目印）

終了時に1回だけ書かれる。**再生時に「この時間から見たい」を実現するためのもの**。

| 順番 | 名前 | 型 | 説明 |
| --- | --- | --- | --- |
| 1 | count | `varint` | 目印の数 |
| 2 | 目印 | `varint` 時間(ms) + `varlong` ファイル位置 | これを count 個くり返す |
| 3 | durationMs | `varlong` | 録画の総時間 |

既定では5秒おきに1個（1時間で720個＝十数KB）なので、録画中のメモリにも優しい。

## パケットが記録される範囲

| 方向 | 記録されるタイミング |
| --- | --- |
| S2C | `ClientConnection#channelRead0`（バニラがパケットを処理する直前） |
| C2S | `ClientConnection#send(packet, listener, flush)`（送信キューに入る直前） |

どちらも「パケットリスナーが `ClientPlayNetworkHandler`（＝ PLAY フェーズ）のとき」だけ記録する。
ログイン・コンフィグレーション・サーバーリスト取得などの通信は一切記録しない。

**自分の移動パケット（`PlayerMoveC2SPacket` 系）は、設定で C2S を切っていても残す**
（v5〜）。再生時のカメラはここからしか復元できないため。他の C2S は再生で使わないので、
設定どおり捨てて容量を節約する。

## 互換性の方針

- バージョンを上げるときは **ヘッダの `version`** を上げる
- 知らないタグが出てきた読み込み側は **そこで読み込みを打ち切る**（壊れたファイルとして扱わない）
- 知らない `TAG_LOCAL` の種類は読み飛ばす（パーティクルが出ないだけで壊れない）
- パケットの中身（ワイヤ形式）は Minecraft のバージョンに強く依存する。
  **`identifier` を残しているのは、将来バージョン間の差し替え・読み飛ばしを可能にするため**

バージョンの履歴:

| バージョン | 変わった所 |
| --- | --- |
| v1〜v3 | 1パケットずつの圧縮（v2〜v3 は辞書を共有） |
| v4 | パケットをかたまりにまとめて圧縮（`TAG_BLOCK`） |
| v5 | `TAG_INPUT` に種類を明示・パーティクルのまとめ書き・C2S無効時も移動パケットを残す |
| v6 | かたまり・パケットに zstd（`method = 2`）を追加。かたまりの大きさを設定ごと（64KB〜1MB）に |
