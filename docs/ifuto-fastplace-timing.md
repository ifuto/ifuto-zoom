# 高速設置のタイミングと「実際の操作」（0.5.1）

## 1. なぜ tick で撃つと検知されるのか

Minecraft のクライアントは 20Hz（50ms 固定）で tick する。設置を tick で撃つと、
サーバーに届く設置の時刻は **必ず 50ms の倍数**になる。

```
50, 50, 50, 100, 50, 50, 100, 50 …
```

人間の連打はこうならない。間隔は 40〜90ms のあいだを連続的にばらつき、
同じ数字が二度続くことすら稀になる（Fitts & Peterson 1964 の運動時間分布、
Wing & Kristofferson 1973 のタイミングモデル）。つまり
**「50 が並ぶ」こと自体が機械の署名**で、統計モデルをどれだけ凝っても
最後の丸めで台無しになっていた。

## 2. フレーム単位で撃つ（0.5.1）

* 実際に置くのは `FastPlaceModule.frameStep`（`FastPlaceFrameHook` から毎フレーム）。
* 予定時刻 `dueAtMs` は tick 境界に丸めない。間隔は ms 単位の連続値。
* 撃つのはバニラと同じ入口 — `ClientPlayerInteractionManager#interactBlock` +
  `PlayerEntity#swingHand`。パケットを自前で組み立てることはしない。
  だから設置音・腕振り・CPS 表示 Mod・キー表示 Mod までバニラの操作と同じに見える。
* そのぶんバニラ自身の `doItemUse`（右クリック長押しでの自動設置）は
  `itemUseCooldown` を大きめに保って止める。撃つ瞬間だけ 0 に戻す。

## 3. 同じ数字を続けない

`ClickTimingModel` に **再出現禁止則**を入れた。

* 直近 4 回の間隔を覚えておく。
* 新しい間隔がそのどれかと `REPEAT_WINDOW_MS = 6ms` 以内なら、
  「6ms + 平均の 10% 以内」だけ上下にずらして引き直す（最大 20 回）。
* それでも決まらないときは履歴の最大／最小の外へ押し出す（必ず決まる）。

丸めた ms で比較するので、「50 と 52」「50 と 50」のような
**近似値の連続**も出ない。

## 4. 「押したことにする」キー（キー表示 Mod 対策）

クリスタルのようにモジュールが代わりに操作する場面でも、キー表示 Mod に
押下を見せたい。ここで `KeyBinding#setPressed` を触ると本物の入力が壊れるので、
**読み取りだけ**に細工をする（`mixin/KeyBindingMixin`）。

* `VirtualKeys.press(binding)` で 120ms のあいだ「押されている」と読ませる。
* 本物の押下状態（`setPressed` / `timesPressed`）は一切触らない。
* モジュール自身の判定は `VirtualKeys.physical(binding)` を使い、
  自分の細工を拾わないようにする。
* mixin は `require = 0`。メソッド名が変わった環境でも起動は壊れない
  （その場合キー表示 Mod にだけ映らなくなる）。
